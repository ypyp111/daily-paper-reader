## 摘要
由人工智能/机器学习驱动的代理正在深入融入编排过程。工作调度是接收请求、将其转换为工作负载管理器所需格式并成功提交的任务。在多集群环境中运行科学工作流带来了动态作业转换、调度和提交到异构集群的重大挑战。这些任务非常适合代理，它们可以接收工作的文本指令、准备作业规范并进行调度。在这项工作中，我们评估了一个调度代理在432次运行中的可靠性，测试了四种提示风格下五个特征维度的所有可能组合。该代理高度可靠（成功率为97.9%）。我们在多集群实验中测试了完整的编排流程，包括提交、排队、匹配、评分、选择、转换和调度。我们发现，描述性元数据将220个提交作业的成功执行率从48%提高到87%，消除了架构不匹配，并将十个可测量应用中的五个性能提升了高达3.3倍。

## Abstract
Agents powered by AI/ML are becoming ingrained in orchestration. Dispatch of work is the task of receiving a request, transforming it for a workload manager, and successfully submitting it. Running scientific workflows across multi-cluster environments introduces substantial challenges of dynamic job transformation, dispatch, and submission to heterogeneous clusters. These tasks are well-suited to agents, which can receive textual instructions for work, prepare job specifications, and dispatch. In this work, we assess the reliability of a dispatch agent across 432 runs, testing all possible combinations of five feature dimensions across four prompt styles. The agent is highly reliable (97.9% success). We test a full orchestration to submit, queue, match, score, select, transform, and dispatch in a multi-cluster experiment. We find that descriptive metadata increases successful execution from 48% to 87% of 220 submitted jobs, eliminating architecture mismatch, and improving performance for five of ten measurable applications by up to 3.3x.

### 一、核心问题与整体含义（研究动机和背景）

- **研究背景**：AI/ML驱动的计算代理正逐渐成为工作流编排的核心组成部分。在高性能计算（HPC）领域，未来中心需要从传统的结构化作业脚本提交模式，转向用户以文本形式描述资源需求、时间优先级、成本和性能偏好的新模式。
- **核心问题**：在跨多集群环境中运行科学工作流，面临动态作业转换、异构集群上的作业调度与提交等重大挑战。传统多集群调度工具（如Federated Slurm、Kueue、Volcano等）多采用“最先可用”策略，而非“最佳匹配”，可能导致性能损失或成本增加。
- **整体含义**：本文系统评估了AI代理在HPC工作调度（dispatch）中的可靠性和准确性，并验证了描述性元数据（descriptive metadata）在多集群调度中对作业执行成功率和性能的关键价值，为“未来HPC中心”的自主化编排提供了可行性证据。

### 二、论文提出的方法论

1. **Secretary Agent软件架构**：
   - 基于资源秘书（resource secretary）软件，实现了超过50个真实和模拟的provider（工作负载管理器、存储、网络等）。
   - 通过Model Context Protocol（MCP）服务器实现代理与资源的交互，代理可自动发现可用资源、检查队列、管理作业、探索环境。
   - Flux Framework作为实验中的工作负载管理器，通过Flux Operator部署在Kubernetes上。

2. **作业调度流程（Dispatch Pipeline）**：
   - 代理接收用户文本请求 → 调用provider接口生成/转换作业规范（jobspec） → 提交到工作负载管理器 → 监控作业状态（至少两次观测） → 验证日志确认成功启动 → 返回含有效作业ID的收据。
   - 每次执行需调用验证工具检查LAMMPS参数（如问题规模、参数格式），出错时修正命令。

3. **提示工程（Prompt Generation）**：
   - 构建组合式提示生成器，覆盖5个特征维度（工作负载管理器、nocite标志、资源、应用配置、亲和性），每个维度有4种变体（exact、descriptive、verbatim、discovery），共产生432种提示组合。
   - 提示模板结构：`Prompt = [Manager] + [Resources] + [Application] + [Modifiers]`。

4. **Fluxq多集群调度控制平面**：
   - 核心组件：队列管理器 + Fluxion图调度器（匹配、评分、选择）。
   - 每个集群表示为一组JSON图格式（JGF）图，包含主容器子系统（节点、核数、GPU、内存）和零个或多个描述性子系统（架构、网络、内存范围）。
   - 调度流程：集群注册 → 作业规范提交 → Fluxion并行匹配各集群 → 按子系统匹配数评分 → 随机洗牌打破平局 → 最高分集群被选中 → 确定性模板转换 → 分发执行。

5. **Artifact Secretary**：
   - 在隔离环境中使用代理探索容器内容，生成描述应用构建的JSON清单（manifest），包括架构、应用名称、二进制文件、依赖和能力列表。

### 三、实验设计

#### 实验1：调度代理可靠性评估（432次运行）

- **场景**：5节点AWS EKS Kubernetes集群（hpc7g.16xlarge × 5），Flux Framework + LAMMPS ReaxFF模拟（问题规模32×32×16，5节点共320任务）。
- **基准**：手动执行的黄金标准（gold standard）运行，对比代理执行性能。
- **提示矩阵**：5特征×4变体×2次重复=432次组合运行，每次执行后完全清空Flux队列。
- **评估指标**：作业执行成功率、工具调用分布、命令/作业规范准确性、提示风格与成功率关联。

#### 实验2：多集群调度实验（220次运行）

- **集群规模**：6个集群，分布在AWS和Google Cloud（GKE），覆盖amd64/arm64架构、不同网络（EFA、gVNIC、以太网）、内存范围（8–256GB）和成本（0.29–3.78美元/小时）。
- **应用集合**：11个应用（Kripke、LAMMPS、AMG2023、HPL/LINPACK、miniFE、mixbench、OSU AllReduce amd64/arm64、Quicksilver amd64/arm64、STREAM），容器来自219个容器的可用性研究库。
- **两种条件**：
  - **基准条件（base）**：不包含子系统需求，所有集群均可行且等概率随机选择。
  - **子系统条件（subsystem）**：包含架构、网络、内存等描述性需求。
- **配对设计**：每个应用-条件配对运行10次，共110对、220次运行。
- **执行环境**：所有集群部署Flux Operator MiniClusters，flux-secretary代理接收参数、从环境推导资源、提交并监控作业，允许最多10次重试。

### 六、主要结论与发现

1. **代理调度高度可靠**：432次运行中423次成功（97.9%），性能与人工黄金标准无显著差异。
2. **失败模式**：仅2/9与代理相关（如输入参数拼接错误——句点代替空格）；7/9为Flux环境问题。
3. **描述性元数据显著提升执行成功率**：基准条件下仅48%作业成功执行（53/110），子系统条件下提升至87%（96/110）；失败主要是架构不匹配（43/57）。
4. **消除架构不匹配**：子系统条件确保arm64容器不落入amd64集群，减少无效执行。
5. **性能提升**：子系统选择使五个应用性能提升——MiniFE（3.32×）、AMG2023（1.46×）、Stream（1.21×）、Mixbench（1.11×）、LAMMPS；OSU arm64的延迟在所有十种消息规模中降低（中位数1.66×）。
6. **分配的随机性验证**：基准条件下作业在各集群分布均匀（15–21个/集群），证明匹配和评分机制正确；子系统条件下映射到7–28个/集群，符合应用需求。
7. **描述性元数据的作用是排除而非优化**：它主要防止了最坏情况（无法运行的集群），而非一致的性能优化工具。

### 七、优点

- **系统性提示分析**：首次对5特征×4提示风格的完整组合矩阵进行评估，为提示工程提供数据驱动指导。
- **端到端多集群编排验证**：Fluxq将队列、匹配、评分、选择、转换、分发的完整流程在真实云环境中实现并验证，而不只是单集群模拟。
- **软件工件的完整交付**：贡献了Secretary Agent、Artifact Secretary、Flux Secretary、Fluxq等软件，具备可复制性。
- **严谨的评估协议**：要求代理至少两次观测，防止幻觉；可编程验证作业ID、状态和日志；执行间清空队列。
- **层级抽象设计**：从“意图”（高层）到“机制”（低层）的解耦，先匹配高层资源需求，再由执行端细化命令，避免过早过拟合。

### 八、不足与局限

1. **应用场景有限**：实验1仅测试LAMMPS单一应用；实验2虽有11个应用但部分问题规模小（如Quicksilver无法追踪任何段，FOM为零），性能对比数据量有限（如Mixbench仅2 vs 5可比较）。
2. **子系统空间过于简化**：只覆盖架构、网络、内存三个维度，缺乏GPU、存储层级、互连拓扑等更细粒度特征。
3. **代理过早放弃问题**：实验中代理常在首次fabric错误后过早退出，未充分探索环境修正（Quicksilver仅3/20成功）；agent不了解自己的最大重试次数。
4. **LLM非确定性与API可用性**：不同模型/版本可能产生不同结果；实验中5/220运行出现API不可用导致失败，无指数退避机制。
5. **意图传递不足**：flux-secretary只收到分配和命令，不了解更大层次的意图，导致部署中无法合理调整。
6. **性能提升结论需谨慎**：描述性元数据主要帮助是排除，不属于一致的性能优化工具；MiniFE是唯一幅度大且样本充足的结果，其他提升可能混杂噪声。
7. **集群同质性假设**：实验假设每个集群内的节点是同构的，真实环境下节点异质性更复杂。
8. **单次实验偏差风险**：实验1使用特定Gemini模型、实验2使用特定Claude模型，无法泛化到其他LLM。
