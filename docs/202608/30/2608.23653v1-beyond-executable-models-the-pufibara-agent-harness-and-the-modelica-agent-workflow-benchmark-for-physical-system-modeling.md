## 摘要
人工智能智能体越来越多地用于仿真驱动工程。物理系统建模与软件工程中的通用代码生成有不同的要求，因为正确性不仅取决于语法和可执行性，还取决于物理一致性和场景相关行为。我们在 Modelica 中研究这一挑战，这是一种基于方程的建模语言，其中的模型可能编译并模拟成功，但仍然违反其预期的物理或工程要求。在连续的修订中，智能体可能丢失需求，或依赖于由过时候选模型产生的仿真证据。为应对这一挑战，我们提出了 Pufibara，一个智能体框架，它在修订之间维护持续的工程状态，将执行和仿真证据与产生它的候选模型相关联，并使提交成为显式的智能体动作。为了评估端到端的 Modelica 智能体工作流，我们还提出了一种基于源代码的方法，用于构建真实且可独立评估的任务。我们使用该方法构建了包含 232 个任务的 Modelica 智能体工作流基准，涵盖模型修复、模型生成和模型调优。每个提交的候选模型由基准拥有的评估器在智能体循环之外进行评分。我们将 Pufibara 与 Claude Code 作为完整的框架，在两种匹配的大语言模型后端下进行比较。使用 DeepSeek v4 Flash 时，Pufibara 通过 202 个任务，而 Claude Code 通过 185 个。使用 Claude Sonnet 5 时，Pufibara 通过 202 个任务，而 Claude Code 通过 187 个。根据仓库报告的逻辑令牌统计，Pufibara 的逻辑令牌总数降低了 76.4%–82.5%。其顺序运行时间降低了 6.1%–58.4%。这些发现表明，即使在匹配的 LLM 后端下，完整的智能体框架在物理系统建模的任务成功率和资源使用上也可能存在显著差异。

## Abstract
AI agents are increasingly used for simulation-driven engineering. Physical system modeling presents different requirements from general-purpose code generation in software engineering, because correctness depends not only on syntax and executability but also on physical consistency and scenario-dependent behavior. We study this challenge in Modelica, an equation-based modeling language in which a model may compile and simulate while still violating its intended physics or engineering requirements. Across successive revisions, an agent may lose track of requirements or rely on simulation evidence produced by an outdated candidate.   To address this challenge, we present Pufibara, an agent harness that maintains persistent engineering state across revisions, associates execution and simulation evidence with the candidate that produced it, and makes submission an explicit agent action. To evaluate end-to-end Modelica agent workflows, we also propose a source-grounded method for constructing realistic and independently evaluable tasks. We use this method to build the 232-task Modelica Agent Workflow Benchmark, spanning Model Repair, Model Generation, and Model Tuning. Each submitted candidate is scored by a benchmark-owned evaluator outside the agent loop.   We compare Pufibara with Claude Code as complete harnesses under two matched large language model (LLM) backends. With DeepSeek v4 Flash, Pufibara passes 202 tasks, compared with 185 for Claude Code. With Claude Sonnet 5, Pufibara passes 202 tasks, compared with 187 for Claude Code. Under the repository-reported token accounting, Pufibara records 76.4%-82.5% lower logical-token totals. Its sequential runtime is 6.1%-58.4% lower. These findings show that, even under matched LLM backends, complete agent harnesses can differ substantially in both task success and resource use for physical system modeling.

## 1. 论文的核心问题与整体含义

- **研究背景**：物理系统建模（如 Modelica）不同于通用软件工程中的代码生成，其正确性不仅依赖语法与可执行性，更依赖物理一致性和场景相关行为。一个 Modelica 模型可能编译通过、仿真成功，但依然违反预期的物理或工程需求。
- **核心问题**：在智能体迭代修改模型的过程中，可能存在两类关键失败模式：
  - 智能体随时间丢失对原始工程需求的追踪（需求漂移）；
  - 智能体在模型修订后仍使用旧候选产生的仿真证据（证据过期）。
- **整体含义**：可执行性不是充分停止条件；一个完整的智能体工作流需要持久维护工程状态、将证据与产生它的候选绑定，并让“提交”成为显式动作。同时，现有基准缺乏对端到端 Modelica 智能体工作流的评估。本文旨在填补这一空白，首次提出专为 Modelica 设计的智能体框架与基准。

## 2. 论文提出的方法论

### 核心思想
- 将工程需求表示为**持久义务（Engineering Invariants）**，与可观测变量、仿真场景和评判条件绑定；
- 将仿真结果以**候选绑定证据（Candidate-bound Evidence）** 形式记录，防止旧结果污染新候选；
- 将**提交**定义为显式智能体动作，而非编译/仿真成功的隐式结果；
- 官方评估由基准方拥有的独立评估器在智能体循环之外完成。

### 关键技术细节

#### 工程不变量形式化
- 每个不变量表示为四元组：  
  `ik = ⟨pk, O_k, S_k, φ_k⟩`  
  其中 `pk` 为工程命题，`O_k` 为相关可观测集合，`S_k` 为仿真场景集合，`φ_k` 为证据评判条件（定量或定性）。
- 不变量类型包括：物理不变量（守恒/符号/有界性）、工程约束（接口/参数/操作限制）、行为需求（特定场景下的响应）。

#### 候选绑定证据记录
- 证据记录形式化为：  
  `ej = ⟨ik, c, s_j, O_j, Y_j, a_j⟩`  
  其中 `c` 为产生该证据的候选模型，`s_j` 为场景，`O_j` 为观测，`Y_j` 为轨迹或派生量，`a_j` 为智能体的裁决。
- 候选身份变更后，旧证据保留审计历史，但当前候选的就绪状态必须基于新候选产生的证据。

#### 工作流与就绪规则
- 工作流为：  
  `工程简报 → 不变量账本 → 观测与场景绑定 → 候选模型 → 定向仿真 → 证据裁决 → {进一步证据 / 修订 / 提交}`
- 候选就绪条件：  
  `ready(c) ⇔ ∀i ∈ I_req, covered(i, E_c) ∧ supported(i, E_c)`  
  即所有要求的不变量都被覆盖且被当前候选的证据支持。

#### Pufibara 框架架构
- 三个内部组件：
  - **Agent Runtime + Workflow Profile**：定义交互循环、任务表示和提交协议；
  - **Persistent Engineering State**：保存任务上下文、候选身份、执行记录和候选绑定证据；
  - **Transparent Execution Plane**：执行工作区操作、模型检查和仿真，结果与候选绑定。
- 三种工作流配置：
  - **Model Repair**：修复有缺陷的模型；
  - **Model Generation**：从工程简报构建模型；
  - **Model Tuning**：在固定模型上调优参数。
- 算法级别：给出了完整运行协议（Algorithm 1），包括初始化、循环暴露状态、执行动作、显式提交冻结、候选变更记录等。

## 3. 实验设计

### 数据集与 Benchmark
- 构建 **Modelica Agent Workflow Benchmark**，共 **232 个任务**：
  - Model Repair：132 个（容易21 / 中等56 / 困难55）；
  - Model Generation：50 个（容易2 / 中等10 / 困难38）；
  - Model Tuning：50 个（容易4 / 中等24 / 困难22）。
- 任务来源：
  - 140 个直接来自公共模型；
  - 15 个由公共库组件（如 Modelica Standard Library）组合而成；
  - 77 个使用内部作者自建的参考模型。
- 覆盖领域：电气/电磁/机电、热流体/建筑/过程系统、机械/多体、控制/信号/混合动力学。
- 每个任务有 agent 可见任务包和 benchmark 私有评估契约；评估器在提交后运行，不参与智能体循环。

### 评估协议
- 通过条件：`PASS(t,x) = It(x) ∧ Mt(x) ∧ Ct(x) ∧ St(x) ∧ Bt(x)`  
  包括接口检查、模型/参数约束、Modelica 模型检查、仿真成功、行为条件。  
  Generation 和 Tuning 任务都包含行为门，Repair 任务无单独行为门。

### 对比方法
- 比较 **Pufibara** 与 **Claude Code**，在两种 LLM 后端条件下：
  - DeepSeek v4 Flash；
  - Claude Sonnet 5。
- 每个任务在每个 harness-backend 组合下运行一次；相同任务集、Modelica 环境（OpenModelica Docker 镜像）和评估器。
- 主要指标：任务通过数、逻辑 token 使用量（uncached + cache creation + cache read + output）、顺序运行时。

## 6. 论文的主要结论与发现

- **任务成功率**：
  - DeepSeek v4 Flash 下：Pufibara 通过 202/232，Claude Code 通过 185/232；
  - Claude Sonnet 5 下：Pufibara 通过 202/232，Claude Code 通过 187/232。
- **资源消耗**：
  - Pufibara 逻辑 token 总量降低 76.4%–82.5%；
  - 顺序运行时间降低 6.1%–58.4%。
- **优势分布**：
  - 所有 6 个 workflow × backend 组合中 Pufibara 均占优；
  - 最大优势在 Model Generation（+16pp 对 DeepSeek，+12pp 对 Claude Sonnet）；
  - 在 38 个硬生成任务（Claude Sonnet 5 下），Claude Code 有 21 个可执行但行为不正确的最终提交，而 Pufibara 仅 4 个。
- **核心发现**：
  - 即使 LLM 后端、任务、环境、评估器匹配，完整智能体框架的设计仍会显著影响物理系统建模的任务成功率和资源使用；
  - 可执行性不等于工程正确性，候选绑定的证据和持久工程状态是提升智能体可靠性的重要因素。

## 7. 优点

- **问题定义清晰**：明确区分可执行性与物理/工程正确性，将不变量、证据、候选身份、提交联系起来。
- **方法论创新**：提出“工程不变量账本”和“候选绑定证据”机制，直接应对需求漂移和证据过期问题。
- **基准构建方法务实**：采用“源代码接地”的任务合成，利用真实模型作为物理基础，同时通过新故障/新简令/新调优目标/私有契约避免直接记忆，降低预训练污染风险。
- **独立评估边界**：评估器在智能体循环之外，使用冻结契约，防止自我验证，并显式验证评估器对已知正确/错误答案的判别能力。
- **全面评估**：在多个工作流、多个领域、两个 LLM 后端下比较完整框架，并区分失败发生在可执行性阶段还是行为阶段。

## 8. 不足与局限

- **统计显著性缺失**：每个条件只运行一次，无法评估运行间波动，结论不能说明显著性或普适性。
- **无消融实验**：端到端比较无法确定哪些机制（持久化、证据绑定、显式提交等）贡献了多少。
- **预训练污染风险无法完全消除**：公共模型和组件可能已出现在 LLM 训练数据中，尽管新任务构造降低了直接复现风险。
- **Repair 任务无行为门**：只检查接口、模型检查和仿真，不评估行为正确性，可能低估该工作流的语义难度。
- **评估范围受限**：PASS 仅针对固定仿真场景和私有契约，不是形式化验证；不覆盖所有运行条件。
- **资源度量标准化局限**：token 统计是跨 harness 归一化的操作测量，不是供应商账单；运行时间依赖特定执行环境。
- **通用性有限**：只验证了 Modelica 语言、Claude Code 一个对比框架、两个 LLM 后端，未覆盖工业专有工作负载。
- **算力细节缺失**：未提供 GPU/基础设施等具体资源信息，不利于复现资源成本评估。
