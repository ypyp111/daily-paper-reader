## 摘要
AutoMOOSE是一个智能代理软件框架，将自然语言请求转换为已执行、已筛选且已解释的MOOSE相场模拟。在本文中，我们将AutoMOOSE作为智能代理软件进行部署，补充了我们先前专注于开发该智能代理工具的工作。我们通过1+5架构视图模型的用例视图和逻辑视图来描述我们的软件框架和架构，涵盖其用户角色、组件结构、六智能代理流水线、物理插件层、模型上下文协议接口以及筛选/证伪/恢复循环。我们的架构将物理证伪与自动修复分离，因此修正后的模拟保持可检查性，并且必须在接受之前重新准入。我们专注于AutoMoose框架的软件设计、可扩展性、互操作性和重用，以便广泛用于多物理场材料设计问题。

## Abstract
AutoMOOSE is an agentic software framework that converts a natural-language request into an executed, screened, and interpreted MOOSE phase-field simulation. Here, we deploy AutoMOOSE as a agentic software, complementing our prior work which focused on development of the agentic tool. We describe our software framework and architecture through Use Case and logical views of the 1+5 architectural-views model, covering its user roles, component structure, six-agent pipeline, physics plugin layer, Model Context Protocol interface, and screening/falsification/recovery loop. Our architecture separates physical falsification from automatic repair, so corrected simulations remain inspectable and must be re-admitted before acceptance. We focus on software design, extensibility, interoperability, and reuse of the AutoMoose framework for broad utilization in multiphysics materials design problems.

## 2. 方法论：核心思想、关键技术细节与算法流程

### 2.1 核心思想

AutoMOOSE 的核心理念是**“筛选/证伪/恢复”循环与“检测-修复分离”**：一个智能代理（Skeptic）负责检测物理上不合理的结果，但从不修复；另一个独立的闭环模块基于其判断采取行动。修正后的模拟必须经过独立的重新准入才能被接受，使得自动修正过程保持透明、可审查。

### 2.2 整体的软件架构（四层结构）

- **接口层（Interface）**：两个入口——用于交互式使用的 React 前端（App.jsx）和用于程序化客户端的 Model Context Protocol（MCP）服务器（mcp_server.py，提供十个工具）。
- **后端层（Backend）**：FastAPI 服务器（server.py，端口8000），负责协调六智能代理流水线。
- **代理层（Agents）**：即六个智能代理构成的流水线。
- **插件层（Plugins）**：物理解析通过插件目录实现，通过 plugin_registry.py 自动发现加载。

### 2.3 六智能代理流水线

流水线的组合公式为：

```
S = f_5 ∘ f_6 ∘ f_4 ∘ f_3 ∘ f_2 ∘ f_1 (U)
```

其中U是用户请求，各函数按运行顺序为：

| 函数 | 代理名称 | 职能 |
|---|---|---|
| f₁ | Architect | 制定结构化模拟计划 |
| f₂ | Input Writer | 编写完整的MOOSE输入文件（.i文件） |
| f₃ | Runner | 执行模拟（本地直接或HPC通过SLURM提交sbatch） |
| f₄ | Reviewer | 执行级筛选：确认运行是否完成、输出是否存在且可解析 |
| f₆ | Skeptic | 物理不变性证伪，测试守恒、渐近极限、对称性、标度关系，返回可信或证伪结果，但不修复 |
| f₅ | Visualization/Interpretation | 在客户端应用层消费运行记录，渲染图形并生成自然语言解释 |

注意运行顺序为 f₁ → f₂ → f₃ → f₄ → f₆ → f₅，即** Skeptic在Visualization之前完成证伪**。

### 2.4 筛选/证伪/恢复循环

- **检测的三个层次**：筛选（f₄，执行级检查）、证伪（f₆，插件特定的物理不变量验证）、恢复（recovery.py，仅针对诊断出的可恢复失效应用预定义的数值修正）。
- **恢复的三种有界修正**：时间步二分减半（下限 MIN_DT0 = 1.0 ns）、延长积分窗口（上限 MAX_END_TIME）、网格精化增加（上限 MAX_REFINE）。
- **恢复的硬约束**：
  - 每次任务最多三次尝试（MAX_ATTEMPTS = 3）。
  - 修正只涉及数值/离散化控制，**永不改变材料常数或自由能系数**等物理参数。
  - 每次修正都会有 {from, to, why} 格式的变更记录。

### 2.5 Skeptic 的实现示例

以晶粒生长为例，Skeptic 实现两个不变量（skeptic.py 中）：

- **T1 单调性**：晶粒数量不得自发增加，要求无大跳跃且无持续净上升。
- **T3 抛物线（Burke-Turnbull）**：1/N 对 t 线性，R² ≥ 0.90 且斜率为正。

### 2.6 物理插件机制

插件是一个包含 PLUGIN 元数据字典和 generate_input(**params) 函数的目录，可以提供可选 parse_results()。registry 在启动时自动发现插件目录，**添加新物理无需更改代理或后端**。发布版本包含两个"ready"插件（grain_growth、spinodal）和两个 stub 插件（solidification、ferro）。

## 7. 优点

- **架构清晰、形式化程度高**：使用 1+5 架构视图模型，不仅有高层描述，还有组件级结构和操作序列图，并遵守跨视图一致性（角色、组件在视图间保持对应关系）。
- **检测与修复分离**：这一设计使"自动修正"不再是一个黑箱，每次修正都有变更记录，可审计、可追溯。
- **插件层设计灵活且可扩展**：自动发现插件目录、生成输入对代理不透明、PLUGIN 元数据字典标准化，添加新物理域或适配新求解器不触碰代理或后端。
- **模型无关的 LLM 客户端**：通过编辑 config.env 即可切换不同语言模型（如 Claude、Qwen、Llama），无需修改代码。
- **运行记录完善**：每次运行生成结构化的记录（含后端、模型身份、物理与参数、输入大小、运行ID、状态、墙钟时间、Reviewer 指标、Skeptic 判定），**记录本身而非重新查询语言模型是溯源与可复现的单位**。
- **MCP 接口设计克制**：筛选、证伪和恢复内嵌于后端流水线，不作为独立工具暴露，避免外部调用者绕过安全验证。参数扫描每次运行独立上下文，避免上下文累积。
- **恢复策略保守且有界**：修正既有限次数上限，又限制在数值/离散化层，不触碰物理参数，合理平衡了自动化与安全性。

## 8. 不足与局限

- **物理覆盖有限**：当前仅两个 ready 插件（晶粒生长和旋节分解），超出注册插件范围的意图不受支持。
- **外部依赖较重**：需要已编译的 MOOSE 二进制；HPC 还需要 SLURM 调度器；语言模型推理依赖外部模型后端及其可用性。
- **证伪能力局限**：Skeptic 仅针对特定物理场当前定义的不变量进行证伪，尚无该物理域不变量定义的物理无法自动筛选。这些是软件编码的有界拒绝标准，**不是物理正确性的证明**。
- **恢复范围保守**：仅处理有界修正证明的失效模式（如时间步发散），扩展到新物理时仍建议人工审查。
- **软件成熟度仍在发展中**：端到端集成测试（solver-in-the-loop）仍在进行中；依赖语言模型后端使得结果在不同模型间可能存在偏差，运行记录虽包含模型标识但仍依赖外部服务。
- **发布级别限制**：两个 stub 插件是开发中的扩展模板，不能视为已验证的物理能力。
