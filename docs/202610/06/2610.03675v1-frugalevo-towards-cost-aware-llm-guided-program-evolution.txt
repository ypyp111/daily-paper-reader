ABSTRACT
LLM-guided evolutionary methods, such as AlphaEvolve, have emerged as pow-
erful approaches for challenging computational optimization problems, such as
circle packing. However, prior work typically optimizes performance gain over a
fixed number of iterations. We argue that practical optimization should maximize
gain per unit cost. To this end, we propose FrugalEvo, a cost-aware evolu-
tionary framework where a stronger, higher-cost LLM explores solution strate-
gies, and a cheaper LLM implements them and iteratively refines the resulting
code. We also design a cache-efficient evolution process, where our harness and
prompts maximize the sharing of prefixes across different evolution steps, to im-
prove cache reuse. To measure solution quality throughout a fixed cost budget, we
introduce Budget-Aware Area Under the Curve (BA-AUC), defined as the area
under the best-so-far evaluation score curve over cumulative LLM cost, up to the
budget. Across 10 mathematical and systems optimization tasks, FrugalEvo
matches or surpasses state-of-the-art baselines, including OpenEvolve, ShinkaE-
volve, AdaEvolve, and EvoX, in final solution quality and achieves higher BA-
AUC on 9 tasks. It also achieves higher average performance than these baselines
on 10 algorithmic optimization tasks from ALE-Bench-Lite. Notably, on circle
packing, FrugalEvo achieves new state-of-the-art performance with GPT-5.6
Terra and Luna for only $1.68 and with GLM-5.3 and its Flash variant for only
$0.55, matching or surpassing all baselines, including multi-agent methods such
as CORAL and SwarmResearch, which cost approximately $50 on average.

INTRODUCTION
Rapid advances in large language models (LLMs) have accelerated scientific discovery across di-
verse domains (Feng et al., 2026b; Liu et al., 2026a; Wang et al., 2026). In particular, LLM-guided
evolutionary methods, such as AlphaEvolve (Novikov et al., 2025), OpenEvolve (Sharma, 2025),
and ShinkaEvolve (Lange et al., 2026), have shown promise in computational optimization prob-
lems, including mathematics (Glazer et al., 2024), systems (Cheng et al., 2025), and algorithmic
optimization (Imajuku et al., 2026). These methods typically maintain a pool of high-performing
programs or solutions; they iteratively select a parent from this pool, prompt an LLM to propose a
mutation, and then evaluate the resulting candidate. Progress is often measured as performance after
a given number of evolutionary iterations (Liu et al., 2026b; Cemri et al., 2026), with curves plotted
against the number of LLM-generated candidates or evaluator calls.
However, focusing on performance after a fixed number of iterations may overlook a key practi-
cal constraint in computational optimization: the total cost. This cost may include API fees or
GPU compute costs for LLM inference, CPU compute costs for evaluator execution, and other
CPU/GPU resource costs associated with task execution. On many challenging tasks, AI agents
achieve better performance with more inference-time computation, a phenomenon known as test-
time scaling (Snell et al., 2024; Brown et al., 2024; Muennighoff et al., 2025). Consequently, higher
performance alone does not establish greater efficiency, as it may simply reflect higher expenditure.
We therefore argue that methods should be assessed by their performance-cost trade-offs and their
ability to maximize solution quality under a fixed cost budget. This shifts the focus from gain per
iteration to gain per unit cost. To measure gain per unit cost, we introduce a new metric, Budget-
Aware Area Under the Curve (BA-AUC), based on the performance achieved at each cost budget.
Next, we propose FrugalEvo, a cost-aware LLM-guided evolutionary framework for computa-
tional optimization. Since LLM inference often accounts for the largest proportion of search costs
in this domain, compared with those of evaluator execution and other CPU/GPU operations, we fo-
cus on improving the cost efficiency of LLM inference. As shown in Figure 1a, FrugalEvo splits
candidate program generation into two steps and uses two different models to carry them out: a
strong, high-cost LLM explores diverse, promising design strategies, while a weaker, low-cost LLM
implements them as executable programs and iteratively refines the resulting code.
Beyond model collaboration, we design a cache-efficient evolution process for FrugalEvo. In-
ference systems and APIs that support prompt caching can reuse cached key-value (KV) states for
identical prompt prefixes, reducing latency and cost. To facilitate this reuse, we design our harness
and prompts to maximize the sharing of prefixes across different evolution steps, improving cache
reuse.
We evaluate FrugalEvo on 20 tasks spanning mathematical, systems, and algorithmic op-
timization (Section 3).
With two model configurations—GPT-5.6 Terra and Luna (OpenAI,
2026), and GLM-5.3 and its Flash variant (Z.ai, 2026a;b)—FrugalEvo matches or outperforms
OpenEvolve (Sharma, 2025), ShinkaEvolve (Lange et al., 2026), AdaEvolve (Cemri et al., 2026),
and EvoX (Liu et al., 2026b) in final solution quality and BA-AUC on 9 of 10 mathematical and
systems optimization tasks. It also achieves the highest average performance across 10 algorithmic
optimization tasks and matches or surpasses the reported AlphaEvolve (Novikov et al., 2025) re-
sults on all four mathematical tasks with available comparisons. Notably, as shown in Figure 1b,
FrugalEvo achieves a sum of radii of 2.63599 on Circle Packing using GLM-5.3 and its Flash
variant for only $0.55, surpassing all baselines, including multi-agent methods which cost approx-
imately $50 on average. Moreover, Figure 1c shows that FrugalEvo substantially reduces the
average cost per iteration.
In summary, our contributions include:
• We argue that practical LLM-guided evolutionary search in computational optimization should
focus on improving performance gain per unit cost. In this work, we introduce Budget-Aware
Area Under the Curve (BA-AUC) to assess solution quality throughout a fixed LLM cost budget,
complementing evaluation based on final scores.
• We propose FrugalEvo, a cost-aware evolutionary framework that combines strategy explo-
ration by a strong, high-cost model with code implementation and refinement by a low-cost
model, and design a cache-efficient evolution process.

2.2
OUR APPROACH
Overview.
Figure 2 presents an overview of our approach, which proceeds as follows: (1) start-
ing from an initial program, the cold start module establishes an “incumbent”—the best-performing
program found so far—as the parent code for strategy exploration and solution generation; (2) the
context builder combines the problem context, task analysis, and incumbent program with informa-
tion from search memory; (3) the strategy explorer uses a high-cost LLM to propose multiple design
strategies; (4) the solution generator uses a low-cost LLM to implement and refine the proposed
strategies; (5) the search memory updates the search context for the next round of strategy explo-
ration; and (6) the process repeats until the budget is exhausted, returning the best program found.
A detailed algorithm description is provided in Appendix A and prompts of strategy explorer and
solution generator can be found in Appendix D.

Figure 2: The FrugalEvo framework. It comprises six main components: (1) a cold-start module,
(2) a context builder, (3) a strategy explorer, (4) a solution generator, (5) an evaluator, and (6) a
search memory. Our search memory uses island-based MAP-Elites (Mouret & Clune, 2015; Tanese,
1989) algorithm.
Cold Start.
The strategy explorer generates design strategies based on a parent program. Using a
weak initial program as the parent may lead to low-quality strategies and inefficient use of the cost
budget. We therefore introduce a cold-start phase in which a low-cost LLM iteratively refines the
initial program until the evaluation score no longer improves. The best resulting program becomes
the initial incumbent and serves as the parent for the first round of strategy exploration.
Context Builder.
The context builder organizes task information and search history to guide strat-
egy exploration. At the start of evolution, the context builder uses a high-cost LLM to analyze the
problem description and evaluator code to identify the optimization objective and evaluation con-
straints. It combines this information with the incumbent program established by cold start and
its evaluation feedback to construct the initial search context. As the search progresses, it updates
the context with the latest incumbent and attempted programs, strategies, and evaluation feedback
retrieved from the search memory, guiding subsequent strategy exploration.
Cache-Efficient Prompt Construction.
Specifically, to reduce input-token costs, we construct
cache-efficient prompts by placing shared content at the beginning, enabling prefix reuse through
API prompt caching.1 To maximize prefix reuse between attempts, each prompt begins with fixed
content (task instructions, output requirements, etc.). This is followed by information which changes
less frequently, e.g., contextual examples, with island-best and elite programs appearing first before
randomly sampled programs, lastly followed by frequently changing information, preserving the
maximum amount of shared prefix across successive attempts. Additionally, feedback from each
attempt is appended to the end of the prompt, allowing cache usage.
Strategy Explorer.
Since algorithmic design can substantially affect solution quality, we use a
strong, high-cost LLM to explore diverse design strategies. Given the search context, including the
parent program, evaluation feedback, and previously explored strategies, it proposes multiple dis-
tinct strategies in a single API call. Each strategy provides a concrete plan for modifying the parent
program, explaining what to change, why it may improve performance, and what computational lim-
its to follow. The proposed strategies are then passed to the solution generator for implementation
and refinement.
Solution Generator.
The solution generator uses a low-cost LLM to implement and refine the
proposed strategies. It first generates one trial implementation per strategy and ranks the strategies

prompt-caching.

by their evaluation scores. It then follows this ranking to select strategies for further refinement.
Each refinement round fixes one strategy and the current incumbent as the parent program, allow-
ing up to M sequential implementation attempts. Each attempt is evaluated, and feedback from
unsuccessful attempts informs subsequent prompts while the parent remains unchanged. As soon
as an attempt improves the incumbent, the round ends, the improved program becomes the new in-
cumbent, and another round begins with the same strategy and the updated parent. If a round ends
without improvement, the generator moves to the next strategy.
Evaluator and Search Memory.
The evaluator assesses each generated candidate program using
task-specific scoring functions. Search memory uses island-based MAP-Elites (Mouret & Clune,
2015; Tanese, 1989) to maintain program diversity. It stores candidate programs and their evaluation
results, along with proposed strategies, the results of strategy attempts, and failure feedback. The
evolution process stops when the remaining budget cannot cover further LLM calls and returns the
best program found.

EXPERIMENTS
3.1
EXPERIMENTAL SETUP
Tasks.
We evaluate FrugalEvo on 20 real-world optimization tasks, including 5 mathemat-
ics optimization problems (Sharma, 2025), 5 systems optimization tasks from the ADRS bench-
mark (Cheng et al., 2025), and 10 algorithmic optimization problems from ALE-Bench-Lite (Ima-
juku et al., 2026). Benchmark details are provided in Appendix B.
Baselines.
We compare FrugalEvo against strong LLM-guided evolutionary methods, includ-
ing OpenEvolve (Sharma, 2025), ShinkaEvolve (Lange et al., 2026), AdaEvolve (Cemri et al., 2026),
and EvoX (Liu et al., 2026b). For mathematical tasks, we additionally report state-of-the-art results
from AlphaEvolve (Novikov et al., 2025).
Model Configurations and Budget.
We use two model configurations in our evaluation. In the
first configuration, FrugalEvo uses GPT-5.6 Terra (OpenAI, 2026) for strategy generation and
GPT-5.6 Luna (OpenAI, 2026) for code implementation and refinement, while all four baselines
use GPT-5.6 Terra. Each run receives an LLM cost budget of $2 per run for mathematical opti-
mization tasks and $1 for systems and algorithmic optimization tasks. In the second configuration,
FrugalEvo uses GLM-5.3 (Z.ai, 2026a) for strategy generation and GLM-5.3 Flash (Z.ai, 2026b)
for implementation and refinement, while other baselines use GLM-5.3. The corresponding budgets
are $1 for mathematical tasks and $0.5 for systems optimization tasks. Model Pricing details are
provided in Appendix C.
3.2
MAIN RESULTS
Results on Math Optimization Tasks.
We evaluate five tasks spanning geometric packing, ex-
tremal geometry, distance-ratio minimization, and multi-objective signal filtering. As shown in Ta-
ble 1, FrugalEvo achieves the highest mean BA-AUC on all five tasks under both model config-
urations. It also achieves the best or comparable mean performance on all five tasks using GPT-5.6
Terra and Luna and four using GLM-5.3 and the Flash variant. Compared to the strong reported
results in the closed-source AlphaEvolve, FrugalEvo matches or exceeds AlphaEvolve on four
tasks, including Circle Packing, Heilbronn Convex (13), Heilbronn Triangle, and Min-Max-3.
Solution Analysis.
Beyond aggregate scores, FrugalEvo discovers qualitatively distinct solu-
tions across different tasks. On Circle Packing, it finds a packing with a total radius of 2.635996
by evolving five-row layouts with asymmetric displacements, refining them through constrained
SLSQP optimization and fixed-center radius linear programming, and applying small radius in-
creases within the evaluator’s tolerance.

ABLATIONS
In this section, we present ablation studies on key components of FrugalEvo (model collaboration,
cold start, and sequential feedback in code refinement) and the results are shown in Table 3.
Impact of Model Collaboration.
Our framework assigns strategy exploration and solution gen-
eration to different models to improve search efficiency. As shown in Table 3, using either the high-
cost or low-cost model for both stages yields lower mean and best performance than FrugalEvo on
both tasks under the same cost budget. In particular, using only the high-cost model leads to a larger
drop in mean performance, possibly because implementation calls consume a substantial portion of
the budget, leaving less for further exploration. Moreover, using only the low-cost model reduces the
best final score, particularly on Signal Processing. This may be because the low-cost model is less
effective at identifying promising strategies. These results suggest that combining strategy explo-

We
introduce a cold-start phase to provide a stronger initial in-

the low-cost model refine programs more effectively and
improves search stability.

RELATED WORK
LLM-Guided Evolutionary Methods.
Recent work combining LLMs with evolutionary search
has produced notable results (Agrawal et al., 2026; Novikov et al., 2025) for mathematical (Feng
et al., 2026c;d;b), algorithmic (Mang et al., 2025), and systems (Cheng et al., 2025) optimization.
For example, FunSearch (Romera-Paredes et al., 2024) combines LLM generation with automated
evaluation to evolve mathematical solutions. AlphaEvolve (Novikov et al., 2025) extends this ap-
proach from evolving individual functions to larger programs. Subsequently, OpenEvolve (Sharma,
2025) and CodeEvolve (Assumpc¸˜ao et al., 2025) provide open-source frameworks, and ShinkaE-
volve (Lange et al., 2026) introduces a sample-efficient evolution method. ThetaEvolve (Wang et al.,
2025) and TTT-Discover (Yuksekgonul et al., 2026) apply Reinforcement Learning (RL) to improve
the LLM generator at test time. More recently, AdaEvolve (Cemri et al., 2026) and EvoX (Liu et al.,
2026b) adapt the search process, while SwarmResearch (Virk et al., 2026) and CORAL (Qu et al.,
2026) coordinate multiple coding agents to improve search performance. These methods focus on
performance gains over a fixed number of iterations, while our work emphasizes gain per unit cost.
Cost-Efficient LLM Inference.
Prior work explores LLM cascades (Chen et al., 2023), rout-
ing (Ong et al., 2025; Feng et al., 2026a), reflection (Agrawal et al., 2026; Zhang et al., 2026a),
and caching (Zhang et al., 2026b) to improve cost efficiency. For instance, FrugalGPT (Chen et al.,
2023) learns model cascades to balance cost and accuracy, while RouteLLM (Ong et al., 2025) learns
to route queries between strong and weak models using preference data. For scientific discovery,
SimpleTES (Ye et al., 2026) post-trains an open-source model for long-horizon AI discovery by
assigning each attempt the final outcome of the trajectory it helped produce. Meanwhile, Squeeze
Evolve (Maheswaran et al., 2026) coordinates multiple models for verifier-free evolution using mod-
els’ own confidence signals, such as token log-probabilities. Our approach allocates model capa-
bility based on the characteristics of computational optimization tasks, without additional model
training or access to token-level probabilities.
5
CONCLUSION
We introduce FrugalEvo, a cost-aware LLM-guided evolutionary framework for computational
optimization, that combines strategy exploration by a strong, high-cost model with code implemen-
tation and refinement by a low-cost model, and design a cache-efficient evolution process. To assess
solution quality throughout a fixed cost budget, we propose Budget-Aware Area Under the Curve
(BA-AUC). Across diverse real-world computational optimization tasks, FrugalEvo matches or
surpasses all baselines in solution quality and achieves higher BA-AUC on the majority of tasks.
Limitations and Future Work.
FrugalEvo splits candidate program generation in computa-
tional optimization tasks into two steps and assigns them to two different models. This design is
9


Preprint
tailored to settings where both solution generation and evaluation take place entirely within a code
environment, so that candidates can be executed and scored automatically. As a result, our method
does not readily extend to scientific domains that require interaction with the physical world, such
as biology, where evaluating a solution may involve wet-lab experiments that cannot be automated
through code execution. Moreover, guiding the model to explore effective strategies relies on care-
fully crafted instructions. Our current instructions are manually designed for computational opti-
mization tasks rather than automatically derived from each task. Finally, future work includes ex-
tending this approach to other domains that require interaction with the physical world, and develop
methods that automatically generate strategy exploration instructions.

Strategy Exploration Prompt
You are the strategy designer for a program-evolution system.
Propose exactly {K} distinct strategies to improve the current
program's evaluated score.
Inputs:
- Task specification and validity constraints
- Current program and evaluated metrics
- Evaluator-aware guidance, when available
- Previous strategies, implementation results, and failures
Each strategy must describe:
1. Mechanism family: a short identifier for the approach.
2. Replacement scope: the function, phase, or block to replace.
3. Compute budget: explicit limits on additional computation.
4. Gain mechanism: the bottleneck addressed or new degree of
freedom introduced.
Propose different mechanisms, not variations in random seeds,
tolerances, or iteration counts. For K >= 3, include local
refinement, subsystem replacement, and structural exploration.
Use previous results to avoid repeating exhausted approaches.
Make every plan self-contained and immediately implementable.
Preserve public interfaces and hard validity constraints.
Do not rely on unavailable tools, fabricated data, or an
unspecified future optimization step.
Explain why the proposed change can improve the actual scoring
objective. Compare quantities on the same scale. End each plan
with a concise gain check: either a justified score estimate
or a testable hypothesis tied to a specific new mechanism.
A fallback or an accept-only-if-better rule is not itself
evidence of improvement.
Return each strategy in this format:
<STRATEGY_TITLE>[mechanism-family] short title</STRATEGY_TITLE>
<STRATEGY>
Mechanism family: ...
Replacement scope: ...
Compute budget: ...
Gain mechanism: ...
Implementation plan and expected-gain check.
</STRATEGY>
When requested, also return one complete, executable portfolio
reference program in <REFERENCE_IMPLEMENTATION> tags.
It is an independent candidate, not assigned to any strategy.
Keep program code outside the strategy blocks.
Code Implementation and Refinement Prompt
You are the implementation model in a program-evolution system.
Implement the supplied strategy to improve the current program.
Inputs:
- Task specification and validity constraints
- Current parent program and evaluated metrics
- Strategy to implement
- Previous implementation feedback, when available
Implement the strategy faithfully. Replace the specified
mechanism and remove superseded code when safe. Do not
substitute an unrelated idea, make only a cosmetic change,
or append another complete optimization pipeline.
Ensure that the new mechanism executes on the normal return
path. Preserve public interfaces, permitted edit boundaries,
and hard validity constraints. Keep added computation within
the strategy's budget. A valid fallback may be retained, but
returning only the fallback does not implement the strategy.
If the parent already implements the proposed mechanism,
refine that mechanism rather than adding a duplicate.
Check dimensions, data types, mutability, API calls, and
consistency between function definitions and call sites.
For a pilot implementation, build the smallest executable
