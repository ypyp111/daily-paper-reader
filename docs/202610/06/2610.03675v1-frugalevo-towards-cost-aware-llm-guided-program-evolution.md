## 摘要
诸如 AlphaEvolve 之类的 LLM 引导演化方法，已成为求解圆填充等具有挑战性的计算优化问题的有力途径。然而，已有工作通常是在固定迭代次数下优化性能增益。我们认为，实际优化应当最大化单位成本所带来的增益。为此，我们提出 FrugalEvo，一个成本感知的演化框架：由能力更强、成本更高的 LLM 探索求解策略，再由成本更低的 LLM 将其实现并迭代优化所生成的代码。我们还设计了一种缓存高效的演化流程，其中我们的运行框架与提示词最大化不同演化步骤之间前缀的共享，以提升缓存复用率。为在固定成本预算下衡量解的质量，我们提出预算感知曲线下面积（Budget-Aware Area Under the Curve，BA-AUC），其定义为在预算范围内，截至当前最优评估得分曲线关于累计 LLM 成本的曲线下面积。在 10 项数学与系统优化任务上，FrugalEvo 在最终解质量上达到或超越包括 OpenEvolve、ShinkaEvolve、AdaEvolve 和 EvoX 在内的当前最优基线，并在 9 项任务上取得更高的 BA-AUC。在 ALE-Bench-Lite 的 10 项算法优化任务上，它的平均性能也高于这些基线。值得注意的是，在圆填充任务上，FrugalEvo 使用 GPT-5.6 Terra 与 Luna 仅花费 1.68 美元即取得新的最优性能，使用 GLM-5.3 及其 Flash 变体仅花费 0.55 美元，即可达到或超越所有基线，包括 CORAL 和 SwarmResearch 等多智能体方法，而后者平均成本约为 50 美元。

## Abstract
LLM-guided evolutionary methods, such as AlphaEvolve, have emerged as powerful approaches for challenging computational optimization problems, such as circle packing. However, prior work typically optimizes performance gain over a fixed number of iterations. We argue that practical optimization should maximize gain per unit cost. To this end, we propose FrugalEvo, a cost-aware evolutionary framework where a stronger, higher-cost LLM explores solution strategies, and a cheaper LLM implements them and iteratively refines the resulting code. We also design a cache-efficient evolution process, where our harness and prompts maximize the sharing of prefixes across different evolution steps, to improve cache reuse. To measure solution quality throughout a fixed cost budget, we introduce Budget-Aware Area Under the Curve (BA-AUC), defined as the area under the best-so-far evaluation score curve over cumulative LLM cost, up to the budget. Across 10 mathematical and systems optimization tasks, FrugalEvo matches or surpasses state-of-the-art baselines, including OpenEvolve, ShinkaEvolve, AdaEvolve, and EvoX, in final solution quality and achieves higher BA-AUC on 9 tasks. It also achieves higher average performance than these baselines on 10 algorithmic optimization tasks from ALE-Bench-Lite. Notably, on circle packing, FrugalEvo achieves new state-of-the-art performance with GPT-5.6 Terra and Luna for only 1.68 USD and with GLM-5.3 and its Flash variant for only 0.55 USD, matching or surpassing all baselines, including multi-agent methods such as CORAL and SwarmResearch, which cost approximately 50 USD on average.

# FrugalEvo 论文总结

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：LLM 引导的演化式程序搜索（AlphaEvolve、OpenEvolve、ShinkaEvolve、FunSearch 等）已在数学发现、系统优化、算法工程等计算优化任务上取得显著成果，其典型范式是维护程序池 → 选择父代 → LLM 变异 → 评估打分。
- **问题**：现有工作普遍以**固定迭代次数下的性能增益**作为评价标准（横轴为迭代轮数或生成候选数），忽略了实际约束——**总成本**（API 费用、GPU 推理成本、CPU 评估开销等）。
- **关键洞察**：在 test-time scaling 背景下，更强的性能可能只是"花更多钱"的结果，而非更高效率；因此应当以**单位成本收益**（gain per unit cost）取代"单位迭代收益"。
- **核心贡献定位**：把评价基准从"性能—迭代"曲线改为"性能—成本"曲线，并提出新指标 **BA-AUC**，同时给出一个成本感知的演化框架 FrugalEvo。

## 2. 方法论

### 2.1 核心思想
- **能力分工**：把"生成候选程序"拆成两步，交给两个不同价位的模型：
  - **高成本强模型（Strategy Explorer）**：负责探索多样化的、有前景的**设计策略**（做什么改动、为什么能提升、算力约束）；
  - **低成本弱模型（Solution Generator）**：负责把策略**落地为可执行代码**并迭代精炼。
- **缓存高效**：通过提示词与运行框架设计最大化**前缀共享**，利用 API 的 prompt caching 降低输入 token 成本。
- **理论依据**：在此类任务中 LLM 推理往往占据搜索成本的最大比例，故优化重点放在 LLM 推理成本上。

### 2.2 问题形式化
- 程序空间 X，初始程序 x₀；评估器 E(x) = (s(x), a(x))，其中 s 为待最大化的任务分数，a 为辅助反馈。
- 程序数据库 D₀ = {(x₀, s₀, a₀)}；第 t 步由搜索策略 S 构造搜索上下文 C_S(D_t)（任务描述 + 父代程序 + 参考程序 + 历史尝试摘要），LLM 依此生成 x_{t+1} 并评估，记录入数据库。
- **优化目标**：在固定成本预算 B 下最大化最优解质量 s⋆ = max s(x)。
- **BA-AUC（预算感知曲线下面积）**：设 q(c) 为累计 LLM 成本 c 时的 best-so-far 分数，则
  **BA-AUC(B) = ∫₀^B q(c) dc**；若某次运行提前结束则在 B 处保持分数不变，超出则截断到 B，以保证所有方法在同一成本区间上可比。

### 2.3 系统流程（六个组件）
1. **Cold Start**：先用低成本 LLM 对初始程序做迭代精炼直到分数不再提升，得到"incumbent"作为首轮策略探索的父代（避免用弱初始程序换取低质策略）。
2. **Context Builder**：用高成本 LLM 一次性分析问题描述与评估器代码，识别优化目标与约束（可缓存）；随搜索推进不断用最新 incumbent、策略与反馈更新上下文。
3. **Cache-Efficient Prompt Construction**：提示词按"变化频率递增"排序——固定指令 → 较少变化内容（岛内最优/精英程序优先，随机采样程序在后）→ 频繁变化内容；每次尝试的反馈追加在末尾，从而最大化可复用前缀。
4. **Strategy Explorer**：单次 API 调用提出 K 个互不相同的策略（机制族、替换范围、计算预算、增益机制），必要时附带一个独立的参考实现程序。
5. **Solution Generator**：每个策略先生成一个试实现并按评估分排序；随后按排序逐策略精炼——每轮固定"一个策略 + 当前 incumbent"为父代，允许最多 M 次顺序尝试，失败反馈进入后续提示；一旦某次尝试超过 incumbent 即结束该轮并开始新一轮，否则转入下一策略。
6. **Evaluator + Search Memory**：任务特定评分函数评估候选；搜索记忆采用**基于岛（island）的 MAP-Elites** 维持多样性，并记录策略、尝试结果与失败反馈。预算不足以支付下一次 LLM 调用时停止，返回最优程序。

### 2.4 算法阶段（Algorithm 1）
- Phase I 冷启动与廉价爬坡 → Phase II 策略探索（K 个策略 + 可选参考实现，若参考实现更优则作为共享父代）→ Phase III 并行试实现与策略排序（按试实现分数 StableArgsort）→ Phase IV 迭代精炼（每策略最多 M 次尝试，Δ ≤ ε 则换下一策略）。

## 6. 主要结论与发现

- **总体**：FrugalEvo 在 10 个数学与系统优化任务上最终解质量匹配或超越 SOTA 基线，并在 **9/10** 任务上取得更高 BA-AUC；在 ALE-Bench-Lite 的 10 个算法任务上取得最高平均私有分（**1924.9** vs OpenEvolve 1887.5、AdaEvolve 1881.9、EvoX 1879.3、ShinkaEvolve 1877.9、ALE-Agent 1822.8）。
- **成本效率**：平均每次迭代成本仅 **$0.0097**，远低于 OpenEvolve $0.0210、ShinkaEvolve $0.0211、EvoX $0.0235、AdaEvolve $0.0435。
- **圆填充 SOTA**：GPT-5.6 Terra/Luna 以 **$1.68** 得到半径和 **2.635996**；GLM-5.3 + Flash 以 **$0.55** 得到 **2.635990**，与平均花费约 $50 的 CORAL（2.635985）和 SwarmResearch（2.635996）相当或更优，实现约两个数量级的成本节省。初始程序仅 0.959764，提升显著。
- **数学任务**：5 个任务在两种配置下均取得最高平均 BA-AUC；在 Circle Packing、Heilbronn Convex (13)、Heilbronn Triangle、Min-Max-3 上追平或超过 AlphaEvolve 报告结果。
- **系统任务**：5 个任务在两种配置下均取得最优或可比的均值/最优性能，4 个任务取得最高平均 BA-AUC（EPLB、PRISM、LLM-SQL、Transaction Scheduling）。
- **解的质性发现**：能发现结构上不同的解法，如圆填充的非对称五行布局 + SLSQP/线性规划精炼、信号处理中 Savitzky–Golay/Butterworth/谱滤波自适应混合、EPLB 的贪心专家复制 + 负载感知块分配 + 成对交换、事务调度的多起点 regret 插入 + 局部窗口重排等。
- **消融结论**：只用高成本模型（Terra+Terra）或只用低成本模型（Luna+Luna）都不如分工方案；去掉冷启动会同时降低均值与最优值；去掉顺序反馈会降低均值并增大方差（稳定性变差）。

- **解的多样性证据**：不仅报告分数，还给出所得解的结构描述（非对称布局、滤波器混合、专家复制+块分配等），为"策略探索确实带来结构性新解而非数值微调"提供了定性支持。

## 8. 局限与不足

- **评估器成本被排除在预算之外**：BA-AUC 只累计 LLM 推理成本。对于评估一次需数秒至数分钟 CPU/GPU 的任务（如大规模启发式仿真、编译运行），评估开销可能远超 LLM 调用成本，此时"成本最优"的结论可能失真；论文虽承认这一点，但未给出任何评估器耗时或算力的量化数据。

- **硬件与运行环境信息缺失**：未报告 CPU/GPU 型号、并行度、单次评估墙钟时间，导致读者无法判断 LLM 成本与计算成本的真实比例，也无法复现时间维度的效率比较。

- **基线复现的可比性存疑**：与 AlphaEvolve 的对比使用其原文报告数字，与 CORAL / SwarmResearch 的对比使用其自报成本（约 $50），既非同预算也非同环境，属于"参照性对比"而非受控实验，结论强度应相应打折。

- **统计功效有限**：每配置仅 3 次独立运行，且未报告置信区间或显著性检验；部分任务（Signal Processing、Heilbronn Triangle）基线方差明显，均值差异可能落在噪声范围内。

- **模型选择的外部效度**：方法依赖"存在一个足够便宜且代码能力尚可的弱模型"这一前提。若低成本模型的实现能力过弱，策略与实现的分工收益可能消失；论文仅在两个厂商的两组模型上验证，未系统研究强弱模型能力差距对收益的影响。

- **预算粒度较粗**：预算取 $0.5 / $1 / $2，未做预算敏感性分析（如 $0.1 或 $10 时 BA-AUC 排名是否稳定），而 BA-AUC 的排序可能随预算区间变化。

- **超参数未充分消融**：K（每轮策略数）、M（每策略最大尝试数）、岛数量与迁移策略等关键超参的取值依据未展开说明，也未做敏感性实验。

- **任务规模有限**：ALE-Bench-Lite 仅 10 题、数学与系统各 5 题，且使用私有分数，外部复现与横向扩展验证受限。

## 9. 对后续研究的启示

- **成本轴应成为演化式搜索的标准报告项**：建议后续工作在报告性能曲线的同时，公开累计成本曲线与定价假设，使不同方法可在同一预算下横向比较；若评估器开销不可忽略，可考虑引入"总拥有成本"（LLM + 计算）作为更严格的成本口径。

- **异构模型分工值得进一步系统化**：本文的"强模型出策略、弱模型写代码"是一个二段式分工。可探索的延伸包括：按策略难度动态路由、让弱模型在失败时主动请求强模型介入、或用强化学习方式学习何时升级模型。

- **缓存友好性应作为提示词设计的一等约束**：在 prompt caching 按前缀命中计价的现实下，提示词的"字段顺序"直接影响成本。本文的"变化频率递增"排序原则可推广为一种通用提示词布局规范。

- **BA-AUC 的改进空间**：可考虑对早期收益加权（如时间价值折现）、或引入"达到目标分数所需成本"作为补充指标，以刻画不同应用场景下对"快速见效"与"最终质量"的不同偏好。

- **与评估成本感知的联合优化**：当评估昂贵时，搜索策略需要同时决定"生成什么"与"是否值得评估"，这类问题可形式化为带评估预算的主动搜索，与本文的纯 LLM 成本视角互补。

## 10. 总结性评价

FrugalEvo 的主要价值不在某个具体任务的 SOTA 数字，而在于**把成本作为一等公民引入 LLM 引导的程序搜索评价体系**：它指出了"固定迭代比较"这一普遍做法在 test-time scaling 时代的系统性偏差，给出可操作的新指标（BA-AUC）与一套与之匹配的框架设计（策略/实现分工、缓存友好提示词、岛式记忆、预算耗尽即停）。在方法层面，其"能力—成本"匹配思路简洁、消融支持充分、工程细节披露到可复现的程度；在实验层面，跨数学/系统/算法三类任务与两个模型族验证了泛化性，圆填充以约两个数量级更低的成本达到 SOTA 尤为有说服力。其结论的适用边界则受限于：评估器成本被排除、统计重复次数偏少、部分对比非受控复现、硬件环境信息缺失。总体而言，本文更应被视作**一次评价范式的倡议与可行性证明**，而非对"成本感知搜索"这一问题的终局解答——它开辟的方向（成本口径的统一、异构模型分工的理论刻画、评估成本与推理成本的联合优化）比它当前给出的答案更具长期意义。
