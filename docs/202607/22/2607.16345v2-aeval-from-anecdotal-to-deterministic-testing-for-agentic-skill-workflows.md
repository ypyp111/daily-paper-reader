## 摘要
现代代理系统越来越依赖于技能：可安装的自然语言和代码包，教会LLM代理执行领域任务。随着技能库的增长，开发人员需要每次变更的自动质量信号，然而目前的评估大多是轶事性的：开发人员让代理"尝试技能"，观看演示，形成主观印象。这既不能保证跨运行的可重复性，也不能保证跨版本的可比性，并且难以扩展到市场上，一个回归问题可能悄然破坏数十个下游工作流。我们提出AEVAL（Agentic Evaluation），一个CI集成的框架，用确定性、可重复的测试管道取代这种做法，用于代理技能。每次技能变更触发测试事件：技能在自动执行器内针对开发者声明的评估合同运行，发出结构化的、基于证据的质量信号，下游CI可以据此路由。一个关键要素是执行器和评分器之间的结构分离，防止一个微妙但普遍的失败模式：代理在执行期间悄然自纠正，然后将自己修补后的输出评为通过。我们的贡献是：(i) 一个确定性、变更触发的评估协议，具有每技能合同和每次运行产物模式；(ii) 将自纠正偏差形式化为朴素代理评估器的一个独特失败模式；(iii) 执行器/评分器分离，使用首次尝试评分规则和显式自纠正跟踪；(iv) 分层的、基于证据修复建议方案（LV1因果，LV2质量），以内联合并请求评论形式发布。在多个代理SDK的生产代理堆栈中的真实技能上验证，AEVAL将虚假的100%通过率转换为可重复的首次尝试失败信号，并具有每次执行器修复的可审计记录。

## Abstract
Modern agentic systems increasingly rely on skills: installable packages of natural language and code that teach an LLM agent to perform a domain task. As skill repositories grow, developers need automated quality signals on every change, yet evaluation today is largely anecdotal: a developer asks an agent to "try the skill," watches a demo, and forms a subjective impression. This yields neither reproducibility across runs nor comparability across versions, and scales poorly to marketplaces where one regression can silently break dozens of downstream workflows.   We present AEVAL (Agentic Evaluation), a CI-integrated framework that replaces this practice with a deterministic, reproducible test pipeline for agentic skills. Every skill change triggers a test event: the skill runs against a developer declared evaluation contract inside an automated executor, emitting a structured, evidence grounded quality signal that downstream CI can route on.   A key ingredient is a structural separation between executor and grader, preventing a subtle but pervasive failure mode: an agent that silently self-corrects during execution and then grades its own patched outputs as passing.   Our contributions are: (i) a deterministic, change-triggered evaluation protocol with per-skill contracts and per-run artifact schemas; (ii) a formalization of self correction bias as a distinct failure mode of naive agentic evaluators; (iii) an executor/grader separation with a first-attempt grading rule and explicit self-correction tracking; and (iv) a tiered, grounded evidence fix suggestion scheme (LV1 causal, LV2 quality) posted as inline merge-request comments. Validated on real skills in a production agentic stack across multiple agent SDKs, AEVAL converts spurious 100% pass rates into reproducible first-attempt fail signals with an auditable record of every executor fix.

## 1. 核心问题与整体含义（研究动机和背景）

- **现状问题**：现代LLM代理系统广泛依赖“技能”（skill）——可安装的自然语言和代码包，用于教导代理执行特定领域任务。然而，当前技能的评估绝大多数是**轶事性的（anecdotal）**：开发者打开交互式会话，让代理“试试这个技能”，观看一次演示，然后形成主观印象判断技能是否“能用”。
- **核心痛点**：
  - 不可复现：两次运行可能走不同代码路径、产生不同输出和不同判断。
  - 不可比较：不同版本之间无法客观衡量质量变化。
  - 无法扩展：技能仓库增长到数十上百个时，一个无声的回归可能破坏多个下游工作流。
- **学术和工程挑战**：即使尝试构建自动化管道，也会遇到**自修正偏差（self-correction bias）**——同一个代理既执行又评分时，它会默默修补技能缺陷，然后将修补后的输出评为通过，从而掩盖技能本身的缺陷。这等价于测量了代理的调试能力而非技能质量。
- **论文目标**：将技能评估从人工的、非正式的“演示测试”转变为**确定性的、可复现的、CI集成的测试管道**，类似于软件工程中的自动化单元测试转型。

## 2. 方法论：核心思想、关键技术细节

- **核心思想**：将每个技能变更视为一个CI触发测试事件。技能必须附带一个显式的评估合同（`eval.config`），声明测试提示、预期结果和所需凭据。框架在干净会话中安装修改后的技能，通过自动化代理执行器运行，发出结构化的、基于证据的质量信号。
- **关键技术细节**：
  - **技能定义评估合同（eval.config）**：与技能代码一起存放，声明多个独立测试用例（prompt、expected outcome、credentials）。执行时每个用例在隔离的SDK会话中运行。
  - **禁止模拟输出**：执行器提示中硬性规则——如果命令失败、服务不可达或流程错误，必须记录为真实失败，不允许伪造日志或占位输出。
  - **执行器与评分器分离**：
    - 评分器是一个独立的子代理（基于固定协议`agents/grader.md`），访问信息集仅包括：测试提示x、只读执行记录τ、输出文件O、以及**执行前写好的断言集合A**。
    - 断言必须在代理观察到输出之前编写，基于技能说明书和预期结果，防止“观测后适配”。
    - **首次尝试评分规则**：评分器针对首次尝试轨迹评估每个断言。如果执行轨迹中包含任何因自我修正而修改技能文件的编辑，且该修正对于断言通过是因果必需的，则即使后续成功，该断言也被标记为 FAIL。
    - 输出结构化`grading.json`，包含每个断言的通过/失败及证据、自修正记录（首次尝试错误、应用变更、受影响断言）、提取的过程和质量声明。
  - **独立分析通过（Analyzer）**：第二个子代理接收汇总的运行指标，撰写自由形式观察（如非判别性断言、不稳定断言、资源异常），不接触技能源码。
  - **分层的、基于证据的修复建议**：
    - LV1（严重）：因果涉及首次尝试失败，必须追踪到 FAIL 断言或自修正记录。
    - LV2（改进）：评分器标识的质量/鲁棒性改进，但不导致硬失败。
    - 每个建议必须附有“grounded in”字段，引用失败断言的确切文本或自修正条目。无此引用的建议被拒绝。
    - 通过GitLab Discussions API以内联建议评论形式发布，开发者可直接点击“应用建议”一键接受补丁。
  - **流水线（五阶段）**：
    1. Examine：检查变更的技能。
    2. Install：在干净会话中安装技能。
    3. Use：按照评估合同执行（禁止模拟输出）。
    4. Evaluate：独立评分器进行首次尝试评分、自修正跟踪。
    5. Suggest：生成分层修复建议并发布到MR。
- **公式/算法流程（文字说明）**：
  - 定义技能s、评估提示x、代理A。朴素评估：运行A(s, x)得到终端状态y，输出q_hat(s) = I[y满足x]。但A的轨迹τ可能包含对技能的编辑Δ(τ)。定义真实质量q*(s) = I[技能首次尝试、未修改时工作]。问题在于q_hat(s) = 1当且仅当A通过任何Δ(τ)恢复，即使q*(s)=0。
  - 解决方案：评分器独立于执行器；使用预写断言A和首次尝试规则；显式记录自修正并将其用于降级通过断言。

## 6. 论文的主要结论与发现

- **主要发现**：
  - 朴素代理评估器由于自修正偏差，会将缺陷技能评为100%通过（如分割技能案例）。AEVAL通过执行/评分分离和首次尝试规则，将虚假通过率转化为可审计的首次失败信号。
  - **因果份额（causal share）**是跨运行时校准的关键指标：不同代理后端在严重性分级上有系统性的不一致（后端A平均0.41，后端B平均0.82），表明需要运行时条件化的校准。
  - **协议忠实度**本身是一个可测量的失败模式：1/6运行未遵守输出模板格式，被框架检测到。
  - **禁止模拟输出规则**有效避免了在资源不可用时生成虚假日志。
  - **基于证据的修复建议**稳定了建议集（重复运行时LV1集收敛），消除了之前版本中建议不重叠的问题。
- **核心结论**：AEVAL框架为代理技能评估提供了结构化、可复现、证据驱动的替代方案，是下游统计方法（如共形预测）生成可靠标签的基础组件。

## 7. 优点：方法与实验设计上的亮点

- **提出并形式化了自修正偏差**：这是之前未被系统研究的代理评估失败模式，论文给出了清晰的形式化定义（q⋆ vs q_hat naive）。
- **执行器/评分器结构分离**：简单但有效的设计，直接防止了自修正偏差。
- **首次尝试评分规则**：将“技能是否工作”与“代理是否修复了技能然后它才工作”区分开，提供更诚实的质量信号。
- **预写断言**：防止“观测后适配”的常见陷阱。
- **分层修复建议并带证据引用**：避免了“考虑添加”式垃圾建议，提高了可操作性；内联MR建议一键应用，闭环测试-修复流程。
- **运行时无关设计**：对外暴露通用接口，已验证多个流行SDK（Claude家族、Codex家族、OpenCode家族），并且跨运行时运行可发现兼容性问题。
- **协议忠实度作为指标**：自身能够检测到输出格式漂移，体现了元评估能力。
- **高缓存效率**：使得频繁CI重跑成本可控。
- **实验设计亮点**：使用了真实生产技能而非合成任务；通过梯度案例（故意降级技能）直观展示偏差；跨运行时校准部分展示了方法的有用性。

## 8. 不足与局限

- **实验数量有限且统计上不充分**：只有6次跨运行时运行、少量定性案例，没有大规模基准测试或严格假设检验。作者自身声明完整的定量研究延期至扩展版本。
- **禁止模拟输出靠指令而非沙箱**：依赖LLM指令遵守，理论上可被攻击或绕过。更干净的方法是沙箱化文件系统写范围。
- **首次尝试规则依赖评分器正确识别因果自修正**：复杂多步修正可能被错误归因，产生假阳性/假阴性。
- **LV1/LV2边界的主观性**：不同代理后端对同根原因严重性判断不一致（因果份额0.41 vs 0.82），缺乏客观校准机制。作者建议未来使用共形校准。
- **无概率覆盖保证**：方法提供的是结构保证而非统计保证，不能替代共形预测等不确定性量化方法，只能作为其输入。
- **未讨论失败代价**：技能在CI中被阻挡的代价与上游PR作者修复代价的权衡未量化。
- **未提供开源实现**（论文中未提及代码仓库），可复现性受限。
- **跨运行时测试计算成本随运行时数量线性增长**。
